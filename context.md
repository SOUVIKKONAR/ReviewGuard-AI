# ReviewGuard — Project and Pipeline Context

This document records how the current repository works, from source data through the ML experiments and web application. It is intended to help a developer or project teammate understand the implementation before changing it.

## 1. Project goal and boundaries

ReviewGuard has two related but distinct analysis paths:

1. **Individual review classification:** classify submitted review text as *truthful* or *deceptive* using a saved supervised text model.
2. **Related-review investigation:** retrieve semantically similar reviews, inspect phrase overlap, and browse review groups formed from Mutual KNN links.

The classification target comes from the Deceptive Opinion Spam hotel corpus. Similarity and groups answer “which reviews are related in this representation?” They do **not** answer “is this group fraudulent?” A repeated phrase, similar meaning, positive tone, or cluster membership is not enough to establish deception.

The system is built around hotel reviews. It must not be described as having been trained on product-review fraud labels. The Amazon Review Polarity dataset is not a deception dataset and is not used as the fake-review target.

## 2. Repository reality and important caveats

- `README.md` is the project guide; this file is the detailed pipeline reference.
- The original empty `app.py` directory was not an application. The current server is `backend/app/main.py`.
- `src/prediction.py`, `src/similarity_detection.py`, `src/group_analysis.py`, `src/clustering.py`, and `src/evaluate_models.py` are empty placeholders. Working implementations live in the other `src` scripts and in the web backend.
- `src/preprocessing.py` contains a general NLTK cleaner, but the trained traditional classifiers do **not** call it. Their vectorizers receive the review text directly.
- `src/feature_extraction.py` contains older helper features (length and promotional-word counts) and a simple TF-IDF helper. Those are not the feature pipeline inside the saved KNN/SVM/Naive Bayes artifacts.
- The current saved traditional models were produced by the random stratified holdout training workflow. The web model page reports separate hotel-independent cross-validation results. Do not imply that a saved model’s individual prediction was generated by a Leave-One-Hotel-Out fold model.
- The processed CSV currently on disk contains 1,600 mapped rows, including four exact duplicate truthful reviews. The active experiments and API remove exact duplicate review text and operate on 1,596 rows (796 truthful, 800 deceptive). The README phrase “verified processed dataset” should not be taken to mean that the file has already been deduplicated.
- In the current processed CSV, `sentiment` contains the same value (`op_spam_v1.4`) in all rows. `src/verify_dataset_mapping.py` assigns `file_path.parts[-5]`, which points to the corpus directory in this layout rather than the positive/negative folder. Do not use this column as sentiment. The original directory structure and `Rating` field hold the source polarity clues; neither is a model feature in the current classifier pipeline.

## 3. Data sources and contents

### 3.1 Primary corpus: Deceptive Opinion Spam

Main source files:

- `DATASET/deceptive_opinion_spam/Chicago_Hotel_Reviews.csv`
- `DATASET/original_corpus/op_spam_v1.4/`
- mapped output: `data/processed/verified_dataset.csv`

The CSV has 1,600 records and columns:

| Source field | Type | Meaning / use |
|---|---|---|
| `Unnamed: 0` | integer | Source row index; not used by the classifiers. |
| `Label` | integer | Deception class: 0 truthful, 1 deceptive. |
| `Rating` | integer | Review polarity represented by 1 or 5 in this source file; not used as a classifier feature. |
| `Ori_Review` | text | Original hotel review text; used as the supervised model input. |

The source contains 800 records with label 0 and 800 with label 1. Ratings 1 and 5 each occur 800 times; each deception class has 400 records at each rating. This balance is consistent with the source corpus’s four strata: truthful-positive, deceptive-positive, truthful-negative, and deceptive-negative, 400 each.

The corpus covers 20 Chicago hotels, initially 80 CSV rows each. The original corpus README describes the source text as coming from truthful reviews on travel sites and deceptive reviews written by Mechanical Turk workers. Original filenames encode class, hotel, and review index, such as `t_affinia_1.txt` or `d_palmer_4.txt`; directory names encode polarity and source split/fold.

The four exact duplicate texts in the processed file are all truthful, and the downstream “keep first” deduplication yields 796 truthful and 800 deceptive unique reviews. The application and prepared experiment outputs use those 1,596 unique texts.

The current 1,596-row processed schema is:

| Field | Type | Meaning |
|---|---|---|
| `review` | text | Review body copied from the CSV. |
| `csv_label` | integer | Original CSV label: 0 truthful, 1 deceptive. |
| `truth_label` | string | Truth mapping recovered from the original corpus: `truthful` or `deceptive`. |
| `hotel` | string | Normalized hotel identifier parsed from the original filename. |
| `sentiment` | string | **Currently incorrect/constant in the generated file** (`op_spam_v1.4`); not used by models. |
| `original_filename` | string | Original corpus filename used to verify class/hotel mapping. |

Review lengths are variable. In the CSV, text length ranges from 149 to 4,158 characters, with a median around 698 characters. The input is unstructured natural language; label, hotel, and provenance columns add the structure needed for supervised evaluation and alignment.

### 3.2 Secondary corpus: Amazon Review Polarity

Files: `DATASET/amazon_review_polarity_csv/train.csv` and `test.csv`.

Each CSV row has three fields and no header: class index, review title, review text. It contains 1.8 million training examples per class and 200,000 test examples per class. In this dataset, class 1 means negative sentiment and class 2 means positive sentiment. Neutral three-star examples were excluded in its source construction.

This dataset is available for unrelated sentiment experiments but is not used to train or evaluate deceptive-review classification. Treating positive/negative labels as truthful/deceptive would be a target-label error.

The large Amazon CSV files (including duplicate copies at `DATASET/train.csv` and `DATASET/test.csv`) are excluded from Git because this app does not use them and the training CSV exceeds standard GitHub file limits. The dataset description file remains tracked.

## 4. From raw data to the structured dataset

`src/verify_dataset_mapping.py` performs the original CSV-to-corpus mapping:

1. Read the hotel CSV and recursively enumerate the corpus `.txt` files.
2. Parse filenames into the `t`/`d` class prefix, hotel identifier, and source review number.
3. Map `t` to `truthful` and `d` to `deceptive`; take the hotel and original filename from the corpus path/name.
4. Normalize text for matching by lowercasing, trimming, and collapsing repeated whitespace.
5. Match each CSV review body to the normalized source-corpus review text.
6. Save the matched review, original CSV label, mapped truth label, hotel, sentiment field, and original filename to `data/processed/verified_dataset.csv`.

The script’s final sentiment path index is off by one for this corpus layout, so its saved `sentiment` value is not the real polarity category. Label mapping itself aligns: CSV label 0 maps to truthful and CSV label 1 maps to deceptive. The model code uses the numeric CSV label; the DistilBERT code maps the verified text label to the same 0/1 convention.

Downstream scripts normalize the working table by dropping null/blank reviews where applicable, trimming text, dropping exact duplicate review strings, and resetting the row index. They do **not** alter or rewrite the original source CSV. The deduplicated row index becomes `review_id` (0–1595) and is the alignment key for the embeddings, similarity matrix, clustered reviews, and saved group reports. Do not sort or otherwise reorder rows without regenerating or remapping those artifacts.

### Preprocessing helpers versus actual model preprocessing

`src/preprocessing.py` defines `clean_text`: lowercase, remove URLs, remove non-letter characters, split, remove NLTK English stopwords, and lemmatize with WordNet. It downloads NLTK resources at import time. This function is **not called by** `src/train_models.py`, `src/hotel_independent_evaluation.py`, or the FastAPI inference service. The trained models rely on TF-IDF vectorizers’ built-in tokenization and lowercase behavior. Changing to the NLTK cleaner at inference would change the model input distribution and is not equivalent to the trained pipeline.

## 5. Traditional supervised models

### 5.1 Features

`src/train_models.py` fits a `FeatureUnion` of two sparse TF-IDF representations on raw review text:

| Branch | Configuration | What it represents |
|---|---|---|
| Word TF-IDF | Word analyzer, unigrams and bigrams, up to 30,000 features, `min_df=2`, `max_df=0.95`, sublinear term frequency, Unicode accent stripping. | Salient words and adjacent word pairs. |
| Character TF-IDF | Character n-grams of length 3–5, up to 20,000 features, `min_df=2`, sublinear term frequency. | Spelling, morphology, punctuation-adjacent patterns, and short character sequences. |

The vectorizer is fit inside the scikit-learn `Pipeline`/`FeatureUnion`, so in cross-validation it is fit on the training fold and then applied to held-out text. Sparse vectors suit short/medium natural-language documents with a large vocabulary and allow linear models to operate efficiently.

### 5.2 Algorithms and tuning

- **KNN:** brute-force cosine distance; grid search over `n_neighbors` = 3, 5, 7, 9, 11 and uniform/distance weighting. It provides a nearest-example baseline. Its high recall in the hotel-independent report comes with lower precision and F1.
- **Linear SVM (`LinearSVC`):** linear margin classifier for high-dimensional sparse features; grid search over `C` = 0.01, 0.1, 1, 10, 100. It gives the strongest traditional hotel-independent F1 in the saved report.
- **Multinomial Naive Bayes:** probabilistic text baseline compatible with nonnegative TF-IDF values; grid search over smoothing `alpha` = 0.01, 0.1, 0.5, 1, 2. It is competitive and has the best result in the separate random holdout report.

The training workflow first removes exact duplicate review texts, then creates an 80/20 random stratified train/test split with seed 42. `GridSearchCV` uses five-fold shuffled `StratifiedKFold` on the training set, optimizes macro F1, and refits the best pipeline on the full training split. The untouched 20% test split is then scored. The fitted pipelines are serialized using joblib to `models/knn.pkl`, `models/svm.pkl`, and `models/naive_bayes.pkl`.

The checked-in `reports/model_comparison.csv` records that random-holdout experiment:

| Model | Accuracy | Precision | Recall | F1 | Best parameters |
|---|---:|---:|---:|---:|---|
| KNN | 81.88% | 77.13% | 90.63% | 83.33% | 9 neighbors, distance weights |
| SVM | 89.69% | 89.44% | 90.00% | 89.72% | `C=10` |
| Naive Bayes | 91.25% | 90.24% | 92.50% | 91.36% | `alpha=0.01` |

These scores should not be mixed with the hotel-independent scores below. The random split can place reviews from the same hotel in both train and test partitions.

### 5.3 Hotel-independent evaluation

`src/hotel_independent_evaluation.py` evaluates whether models generalize to a hotel excluded from training. It uses `LeaveOneGroupOut` with hotel as the group: each of 20 folds holds out one hotel, trains on the other 19, and tests on the held-out hotel. TF-IDF is refit on each fold’s training texts only. The script uses the selected settings KNN `k=9`/distance weighting, SVM `C=10`, and Naive Bayes `alpha=0.01`.

Aggregate predictions across all held-out hotels produce the saved values:

| Model | Accuracy | Precision | Recall | F1 |
|---|---:|---:|---:|---:|
| KNN | 79.45% | 74.03% | 90.88% | 81.59% |
| SVM | 89.85% | 91.00% | 88.50% | **89.73%** |
| Naive Bayes | 89.22% | 90.78% | 87.38% | 89.04% |

Here precision/recall/F1 treat label 1 (deceptive) as the positive class. SVM is the strongest traditional model by this evaluation’s F1, with Naive Bayes close behind. The evaluation output includes fold CSVs, an all-review out-of-fold prediction file, a comparison CSV, and JSON metrics under `reports/hotel_independent/`.

The saved files in `models/` are the pipelines created by the random-stratified training script, not a single Leave-One-Hotel-Out model. The performance page intentionally reports the hotel-independent experiment as a research comparison; it does not claim those metrics are the live artifact’s calibration.

## 6. Transformer experiment: DistilBERT

`src/distilbert_evaluation.py` evaluates `distilbert/distilbert-base-uncased` with five `GroupKFold` splits grouped by hotel. Each fold has disjoint train/test hotel sets. Reviews are tokenized with truncation and padding to a maximum of 256 tokens. The script uses batch size 8, three epochs, AdamW with learning rate `2e-5` and weight decay `0.01`, a linear learning-rate schedule with 10% warmup, gradient clipping, and mixed precision when CUDA is available. Seed 42 is used for reproducibility.

An SVM using the same word/character TF-IDF features and `C=10` is trained on each same hotel split as a matched baseline. Saved aggregate results are:

| Model | Accuracy | Precision | Recall | F1 |
|---|---:|---:|---:|---:|
| DistilBERT | 87.97% | 85.10% | 92.13% | 88.48% |
| SVM on the same five folds | 88.66% | 89.63% | 87.50% | 88.55% |

The models trade off precision and recall and have very similar F1. The evidence does not support claiming DistilBERT is superior to SVM. The repository contains fold results, predictions, and metrics under `reports/distilbert/`, but no saved serving checkpoint. Thus the API does not serve DistilBERT predictions; it serves the saved scikit-learn models.

## 7. Semantic similarity

`src/semantic_similarity.py` encodes the 1,596 deduplicated reviews with `sentence-transformers/all-MiniLM-L6-v2`. It normalizes 384-dimensional embeddings and uses CUDA when PyTorch reports an available GPU, otherwise CPU. Cosine similarity between normalized vectors is their dot product.

Outputs under `reports/semantic_similarity/` include:

- `review_embeddings.npy`: 1,596 × 384 normalized embedding matrix.
- `similarity_matrix.npy`: 1,596 × 1,596 cosine similarity matrix; diagonal is set to -1 so a review does not retrieve itself.
- `similar_reviews.csv`: top 10 nearest corpus records per review.
- `suspicious_pairs.csv`: unique upper-triangle review pairs whose similarity met the exploratory 0.80 cutoff.
- JSON/CSV statistics and breakdowns.

There are 1,272,810 unique unordered pairs among 1,596 records. The saved summary reports mean pair similarity about 0.4602, max about 0.9256, and 1,641 pairs at or above 0.80. The 0.80 value was an exploratory candidate threshold, not a validated fraud threshold. Similarity is a retrieval signal; it is not a deception classifier.

At inference, review-ID neighbor search reads the existing similarity matrix. Free-text analysis lazily loads the sentence-transformer and compares a new embedding against the saved embeddings; if that model runtime cannot load, the service falls back to lexical Jaccard retrieval. A fallback result is lexical similarity, not MiniLM semantic similarity.

## 8. Semantic clusters and PCA experiments

`src/semantic_clustering.py` runs K-Means on the saved MiniLM embeddings, tries K from 2 through 15, and selects K by cosine silhouette score. The saved full-dimensional run selects K=2 with silhouette about 0.1736. PCA experiments compare 384, 128, 64, 32, and 16 dimensions; lower-dimensional silhouettes can increase, but this does not mean deceptive reviews are separated.

Against the ground-truth deception label, the saved PCA comparison has adjusted Rand and normalized mutual information values close to zero (roughly 0.002–0.004). Semantic clusters therefore represent groups of related language, not truthful/deceptive classes. The UI exposes cluster IDs only as exploratory metadata.

## 9. Mutual KNN review groups

`src/validate_mutual_knn_groups.py` builds separate neighbor graphs from normalized embeddings and cosine similarities. For each review, it selects up to K eligible neighbors inside a chosen scope and filters candidates by a similarity threshold. An undirected edge is kept only when the neighbor relation is mutual. The scopes are:

- `all_hotels`: any hotel can be a neighbor.
- `same_hotel`: candidate neighbors must be from the same hotel.
- `cross_hotel`: candidate neighbors must be from different hotels.

The tested K values are 3, 5, and 7; thresholds are 0.80, 0.85, and 0.90. Connected components of the mutual-edge graph with at least two nodes become groups. A connected component can still contain a chain where two members are connected through an intermediate member; the application’s graph view therefore displays only the direct mutual-KNN edges rather than implying every pair in the group has a direct link.

The provisional demonstration setting is all hotels, K=3, threshold=0.85. Its saved output has 41 groups, 182 grouped reviews, 1,414 ungrouped reviews, and a largest group of 10. It is a candidate configuration, not an empirically proven optimum. Other configurations produce very different group sizes; for example, all-hotels K=7 at 0.80 has a largest component of 142. This sensitivity is one reason not to call group membership a fraud verdict.

`reports/mutual_knn_validation/` contains a configuration summary, group details, group members, and group-pair records. Group-pair CSV rows can repeat the same review pair across configurations; pair-level calculations must deduplicate by review IDs before aggregating evidence.

## 10. Linguistic overlap analysis

`src/linguistic_overlap_analysis.py` adds lexical evidence to the semantic graph:

1. Lowercase each review, tokenize alphabetic words, and remove English stopwords for lexical overlap calculations.
2. Build word sets and bigram/trigram sets; calculate Jaccard similarity as intersection size divided by union size.
3. Use `SequenceMatcher` over tokens to identify the longest common token phrase.
4. Fit a corpus-level TF-IDF vectorizer over 2- and 3-gram phrases (`min_df=2`, `max_df=0.80`, max 50,000 features), then extract shared high-weight phrases for candidate review pairs.
5. Join these indicators to Mutual KNN edge/configuration records and produce pair and group summaries.

Saved analysis summary: 5,012 direct edge/configuration instances but 908 unique review pairs after deduplication; 3,857 same-hotel and 1,155 cross-hotel instances. Mean semantic similarity is about 0.8491, while average word, bigram, and trigram Jaccard are about 0.1142, 0.0397, and 0.0110. Thus similar meaning often has limited exact lexical overlap. Same-hotel vocabulary can naturally overlap, and generic phrases should not dominate a risk interpretation.

The review comparison endpoint looks up pair-level linguistic indicators when they exist and combines them with the saved similarity matrix. Repeated edge instances across KNN configurations must not be counted as independent evidence.

## 11. Group risk: offline experiment versus web indicator

There are two related implementations and they should not be conflated:

### Offline `src/group_risk_engine.py`

This research script builds connected components from a dense similarity matrix at thresholds 0.75, 0.80, 0.85, and 0.90. It calculates group size, average/maximum similarity, density, SVM prediction rate, hotel coverage, and actual deceptive rate for offline comparison. Actual labels in those report outputs are evaluation-only and are not suitable as live risk inputs. This script does not output a validated probability of fraud.

### Application indicator in `backend/app/main.py`

The API uses the saved Mutual KNN group details and computes a transparent heuristic:

```text
score = round(45 × group edge density
            + 25 × cross-hotel indicator
            + 30 × SVM deceptive prediction rate)
```

The cross-hotel indicator is 1 when the group covers more than one hotel, otherwise 0. The result is clamped to 0–100 and labeled Low (<40), Medium (40–69), or High (70–100). The score does not use ground-truth labels and does not increase simply because the group has more possible pairs; density normalizes direct edge count by possible pairs.

The weights and bands are provisional engineering choices, not statistically calibrated. The API/UI label the score experimental; it is a prioritization indicator, not a fraud probability. Ground-truth fields in offline experiment CSVs are for retrospective research only.

## 12. How prediction responses work

At backend startup, `backend/app/main.py` reads and deduplicates the review CSV, loads the three joblib pipelines once, memory-maps the saved embedding and similarity arrays, and loads the group/linguistic/cluster/metric outputs. Large group-pair and linguistic files are loaded with only the columns the API needs. The application does not run model training or regenerate analysis reports during startup.

For pasted text, the API calls the selected saved pipeline’s `.predict([text])` and maps 0 to Truthful and 1 to Deceptive. For confidence display, it uses the maximum `predict_proba` score where available; `LinearSVC` has no `predict_proba`, so its absolute decision margin is passed through a sigmoid-shaped transform. Neither value is calibrated as a probability of fraud, and the API explicitly labels it a model score.

For an existing review ID, the service returns corpus metadata and the saved SVM prediction, then reads its top neighbors from the precomputed similarity matrix. Dataset ground truth is exposed for corpus exploration and offline comparison, but it is not part of the operational group-risk calculation.

## 14. Frontend flow

The UI entry point is `frontend/src/main.tsx`; routing, page components, and layout currently live in `frontend/src/App.tsx`, with responsive styles in `frontend/src/style.css` and HTTP setup/types in `frontend/src/api.ts`.

The dashboard requests summary and chart data. Review analysis posts text/model selection and renders the model output and similar records. The explorer requests paged records with search/label/hotel filters. Group filters call the saved validation configuration endpoint, and group details display member records plus direct graph edges. Comparison posts two review IDs. Model, dataset, and system views use their dedicated backend endpoints. Controls shown in those views are connected to real data; loading, empty, and API error states are rendered in the UI.

## 16. Interpretation and known limitations

- The primary corpus is small (1,596 unique reviews) and domain-specific (20 Chicago hotels); performance should not be generalized automatically to products, other regions, or current review platforms.
- Random split scores and hotel-independent scores answer different questions; keep them separate.
- The model score displayed in the app is not a calibrated probability or proof.
- Semantic similarity can reflect shared topic, hotel amenities, or ordinary phrasing. Similarity threshold 0.80 is exploratory.
- K-Means clusters are not deception categories; label alignment in the PCA comparison is near zero.
- Mutual-KNN connected components can contain indirect chains. Inspect direct edges and the actual review text.
- Group count and sizes are sensitive to K, threshold, and scope; the demonstration setting is provisional.
- The app’s risk bands/weights have not been validated against a held-out fraud-risk target.
- The current processed `sentiment` field is erroneous and should be corrected only with a deliberate data regeneration and alignment review.
- DistilBERT results are available as reports, but there is no deployed model artifact for live transformer predictions.
